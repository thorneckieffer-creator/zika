## 2026-11-22 — the adapter speaks to Supabase by hand: no client library

Step 5 was built on the branch `backend`, since merged into `engine` (`js/sync-supabase.js`, 410 lines; `tools/adaptertest.mjs`; `db/0003`, `db/0004`; its account in `docs/backend.md` on that branch). It is not on `main`: a file under `js/` that the page does not load fails the release check, so it comes in with the accounts release (step 8).

- **No pinned copy of the Supabase client library.** This changes one line of the 16 November entry. The library was read before deciding (`@supabase/supabase-js` 2.118.0, 218 KB): it refreshes tokens on a 30-second interval of its own, rejoins a channel on its own schedule for ever, signed in or not, and re-runs session recovery whenever the page comes to the front. Each of those is the kind of timer Thorne's first rule forbids, and each would have to be switched off or worked round. What the app needs of it is four database calls, one channel and seven sign-in calls; `tools/dbtest.mjs` already spoke those three doors by hand. The cost: token exchange, session storage and the channel are ours to keep right, and nothing coordinates two tabs (the engine's lock does).
- **The timers the adapter runs, all of them**: a 30-second limit on a request; a limit on a join; the socket's heartbeat every 25 seconds while joined; one timer set for a minute before the token expires; a growing delay between attempts to rejoin a channel that is down, which stops for a person who is signed out. None of them asks for data.
- **One request is made by a timer, once per join, and it is allowed on purpose.** A project nobody has listened to answers a join about a second before its channel delivers anything, and a record written in that second gives no signal (measured: four of four lost, then none). So after a join the adapter asks the database to send one signal (`rec_signal()`, `db/0004`), asks once more 1.5 seconds later if nothing was heard, and says "joined" only when a signal has arrived. That second ask is the one. It carries no data, happens at most once per join and only while joining. Without it every cold start drops the socket and joins again: about nine seconds to "joined" instead of four.
- **Added to the database on the test project**: `rec_read(after, lim)`, which refuses a signed-out caller; an epoch per person, with one for the whole project so that an account a restore removed is still noticed; `account_delete()`, which deletes the caller's own account and rows and leaves the token dead at once (Supabase has no call for a person to delete their own account; the function removes the user's row itself); `rec_signal()`.
- **Counts**: the real project 125 checks, the model 154, the adapter 38 from Node and 15 in two real browser pages: one page left alone for 35 seconds made no request; when the other wrote, it heard the number and read the row with one request.
- **Not run**: the hour across a token's expiry (`node tools/adaptertest.mjs --soak`); raising the epoch on the real project; anything in Safari or on an iPhone.

## 2026-11-21 — the sync contract is frozen (step 4a), and what the first voice audit found

**The contract** is [sync.md](sync.md), with a model of the database in plain JavaScript (`tools/lib/recmodel.js`) that passes the same checks as the real project (`node tools/dbtest.mjs --model`: 122; the real project: 97). The engine, the adapter, the app-readying release and the accounts module are built against it side by side. What it decides, each with its reason there:

- **The adapter is four calls and the engine does the paging**: `head()`, `write(v, recs)`, `read(after)` (one page), `listen(onSignal, onState)`. The format number is the engine's and is passed in, so the two cannot disagree. An empty page proves nothing: the real project answers a signed-out device's read with no rows and no error.
- **The cursor moves only to the number of the last row applied and stored**, never on an empty page and never to the head's number (expired rows leave the head above anything that can be read).
- **The day's counts are one record per device per day, summed on the device.** The database never looks inside a value, and a device that is offline has to hold its own share anyway.
- **Erase writes a mark that voids the counts up to its day**, not a negative share: negative shares let counts come back when an old device joins.
- **What the app forgets is given a time to live** (three days on a sibling claim, thirty on a snapshot's tombstone), because the database has no "remove". These are judgements; they are settled before anything real is written, since changing them later is a change of format.
- **The engine is attached to the deck as the last statement of start-up**, with no library and no network, and connected later. Edits made on an offline start are then stamped as the edits they are.
- **A generation number in the deck and in the engine's own store** says which of the two is behind: one ahead is a crash between two writes (recover), more than one is a deck written elsewhere (join again by merging), behind is a deck that went back (take the cloud's, then send what was unsent).
- **If IndexedDB cannot be used, sync is off on that device for that run, and says so.** Nothing falls back to localStorage.
- **To be added to the database as `db/0003`** (the adapter's step applies it to `zika-dev`): `rec_read(after, lim)`, which refuses a signed-out caller instead of answering with nothing; an `epoch` per person, raised by hand after a restore, so a cloud that went backwards is noticed; and `account_delete()`.
- **Sending again after a failed write, on a growing delay, is allowed only while there is something unsent.** It is sending, not asking; nothing reads on a timer.

**The voice audit (V0)** ran the tone coach's own analysis over every clip of both packs ([voice.md](voice.md#v0--what-the-audit-found)). Three things change how the Voice plan reads:

- **The tone coach does not grade against the clip.** Its verdict is its classifier against the tone the word should have; the clip is only drawn beside the learner's curve. So a wrong clip teaches a wrong sound, but it does not mark a right tone wrong: a wrong grade is the classifier's. The master plan's sentence that the coach "grades by comparing his pitch with the native clip" describes what V3 would make true, not what the app does today.
- **The analysis cannot yet tell a bad clip from its own mistakes.** On people saying these tones right it is wrong about 12 to 15% of the time. It disagrees with 13.5% of 曉臻's syllables, which is all within that, and with 26.3% of 雲哲's, of which about half is not. The largest single thing is 雲哲's one-character clips: 207 first tones measured as falling. Only an ear settles whether those clips are wrong; the listening page is ready.
- **Thirteen words have one reading in the 注音 file and another in the course's pinyin** (背包, 暑假, 天分, 只要, 古蹟, 待, 除了, 為了, 瓶子, 剛剛, 餓死了, 一會兒, 餡兒). They are settled before any voice is pinned to them in V2.

V1 has no winner: Azure was not run (no key), ElevenLabs stopped at 9 of 62 words (its free queue refused the rest), BreezyVoice was not started (the Mac's swap was full). What each would cost for the full set is in [costs.md](costs.md).

## 2026-11-16 — the dictionary is one entry, opened by tapping a character, built from what the app holds (v65)

## 2026-11-15 — the deck cannot be written by a page that has not started

Splitting the app into files opened a gap that one file never had: the page's buttons work as soon as their script has loaded, and start-up runs in the last script. At one point on `next`, a tap on the theme button in that gap saved the empty default deck over the real one, and a linked device could then send it to the cloud. The independent review found it; the harness scenario `tap-before-start` reproduces it (2,288 cards became 18) and now holds the fix in place. Three things, each enough on its own:

1. The saved deck is read where `S` is defined (`deckLoad` in `js/core.js`), so `S` is never an empty deck while a saved one exists.
2. Nothing writes the deck, the backup file, a snapshot or the cloud before `js/boot.js` has loaded and migrated it (`DECK_READY`).
3. A deck with no cards never replaces a stored one that has cards, and is never pushed from a device that has synced before, unless the learner erased, imported, restored or chose the cloud's copy (`DECK_EMPTY_OK`). Every write of the deck goes through `deckStore()`.

A new way of writing or replacing the deck must go through `deckStore()` and say so with `DECK_EMPTY_OK` if emptying is the point.

A fourth, added when the checker failed v63's first two passes: **an app with a piece missing does not start, and nothing under the "could not start" message can be used.** Start-up used to run to its end with, say, `js/home.js` absent (the missing call was caught), which left the deck open under the message; the keyboard could grade a card there, then Tab and Enter could, a lost stylesheet was never reported, and a file cut off on the way went unnoticed. Now a failed start is any of: a file that does not arrive, a file that cannot be run, a file that did not report running to its last line, a start-up that stops. Then `js/boot.js` starts nothing, the deck is closed, the page under the message is inert and the keyboard goes no further than **Try again** ([architecture.md](architecture.md#start-up)). The price is one fixed last line in every file under `js/`, which the release check enforces.

## 2026-11-15 — a release is stored whole on the device and served from there

Before: the page was fetched from the network on every open (with a 3.5-second fallback to the last copy), and everything else was cached as it was first seen. With the app in thirty files that would have run a new page against old scripts after every release. Now `sw.js` stores the whole shell per release, lists it with a hash of each file (`tools/stamp.mjs`), and serves only from that store. A device takes a release whole or keeps the one it has; opening never waits for the network; an unchanged file is not downloaded again.

The cost is that a release arrives one open later than before: the open that finds it runs the old one while the new one is stored, then reloads into it at once if nothing has been touched, or offers Refresh. That is the price of never mixing versions, and it is what makes splitting the app into files safe.

Since v64 `index.html` asks for each shell file with the release number (`js/core.js?v=64`), written by `tools/stamp.mjs` and enforced by the release check. The worker of v63 and later does not need it: it answers by path and checks content against its hashes. It is for a device still run by the v62 worker, which answers the page from the network and every other file from the copy it first saw at that address. Such a device that had opened v63 once, without v63's worker finishing its install, would have been handed v63's scripts and stylesheet by a v64 page; with part of them stored (an open cut short) it got v64's `js/boot.js` with v63's stylesheet, and the new check of the stylesheet's last rule said "could not start". Reproduced before the number was added and gone with it (the old-worker test, [releasing.md](releasing.md)). v63 itself shipped without the number; that was safe only because v62 had no such files to hold.
